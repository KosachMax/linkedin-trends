В статье рассматриваются новые уязвимости, связанные с использованием больших языковых моделей (LLM) для вызова внешних инструментов. Традиционные модели, генерирующие только текст, имеют один выходной канал. Модели, способные вызывать инструменты, обладают множеством выходных каналов, каждый из которых может быть использован для атаки через инъекцию команд. Контекстное окно модели рассматривается как недоверенный вход, а каждый инструмент — как потенциальный канал утечки данных. Особое внимание уделяется проблеме "внедрения подсказок" (prompt injection) и необходимости анализа безопасности каждого инструмента, включая его возможности чтения и записи.

Расширенный контекст

В статье "Threat modeling LLM tool-calling" обсуждаются риски безопасности, возникающие при интеграции больших языковых моделей (LLM) с внешними инструментами. Традиционные LLM, работающие только с текстом, имеют ограниченный набор выходных данных. Однако, когда LLM наделяется способностью вызывать внешние инструменты (например, для выполнения запросов к базе данных, отправки электронной почты или доступа к файловой системе), количество потенциальных выходных каналов значительно увеличивается. Это создает новые векторы атак, поскольку злоумышленник может попытаться внедрить вредоносные команды в контекстное окно модели, чтобы заставить ее вызвать инструмент нежелательным образом. Автор подчеркивает, что контекстное окно LLM следует рассматривать как недоверенный источник входных данных, а каждый вызываемый инструмент — как потенциальный "сток" для утечки информации или выполнения несанкционированных действий. Проблема "внедрения подсказок" (prompt injection) описывается как разновидность атаки "заблудшего заместителя", где модель выполняет команды, не соответствующие ее первоначальному назначению. Для минимизации рисков предлагается проводить тщательное моделирование угроз для каждого инструмента, доступного LLM, отвечая на вопросы о том, какие данные инструмент читает (особенно секретные), какие данные он записывает, и какие действия он выполняет.

По мере того как большие языковые модели (LLM) становятся все более интегрированными в рабочие процессы и получают доступ к внешним инструментам, вопросы безопасности приобретают первостепенное значение. Уязвимости, такие как "внедрение подсказок", могут привести к серьезным последствиям, включая утечку конфиденциальных данных, несанкционированное выполнение команд и нарушение работы систем. Понимание и устранение этих угроз необходимо для безопасного и эффективного использования мощных возможностей LLM. Разработка надежных методов моделирования угроз и безопасных протоколов взаимодействия между LLM и инструментами является ключевым шагом в обеспечении доверия к этим технологиям и предотвращении потенциального ущерба.

Расширенный контекст

При разработке и тестировании API CourtListener была выявлена серьезная проблема, связанная с обработкой запросов. Для обхода потенциальных блокировок использовалась библиотека curl-cffi, которая имитировала TLS-отпечаток браузера Chrome. Однако, при отправке запросов к API CourtListener, эта имитация привела к непредвиденному поведению. Библиотека отправляла заголовок Accept в формате, характерном для браузеров (например, 'text/html'). Фреймворк Django REST Framework, используемый на стороне сервера, интерпретировал этот заголовок как запрос на получение HTML-представления API, а не на стандартный JSON-ответ. В результате, вместо данных в формате JSON, клиенты получали HTML-страницу API. Эта проблема могла привести к сбоям во всех производственных запросах, так как код, ожидающий JSON, не смог бы обработать полученный HTML.

Обнаруженная ошибка представляла серьезную угрозу для стабильности работы API CourtListener. Если бы она не была выявлена, каждый запрос в производственной среде, использующий имитацию браузера через curl-cffi, завершался бы ошибкой при попытке десериализации полученного HTML как JSON. Это могло привести к полной неработоспособности сервисов, зависящих от данного API. Кроме того, тот факт, что 29 юнит-тестов не смогли обнаружить эту проблему, указывает на потенциальные недостатки в стратегии тестирования. Тесты, которые имитировали слой получения данных (fetch layer), не охватывали реальное взаимодействие с API, что позволило критической ошибке остаться незамеченной до момента ее влияния на продакшен.

Расширенный контекст

В процессе работы с патчами агентов возникла необходимость в более надежных методах их проверки. Собственные тесты, написанные агентом, могут проходить успешно, но это не гарантирует, что система остается корректной. Для решения этой проблемы были разработаны три инструмента: проверки свойств (Property checks) для логики, которая не должна нарушать инварианты; аренды фикстур (Fixture leases) для тестов, взаимодействующих с общим состоянием; и заморозка нестабильных тестов (Flaky freezes) для тестов, которые известны своей ненадежностью, но не могут быть немедленно исправлены. Каждый из этих инструментов имеет свою специфику и предназначен для решения определенных задач. Неправильное использование любого из них может привести к ложному чувству уверенности в корректности патча.

Надежная проверка патчей критически важна для обеспечения стабильности и корректности работы программных агентов. Использование предложенной матрицы решений, включающей проверки свойств, аренду фикстур и заморозку нестабильных тестов, позволяет разработчикам более точно оценивать качество вносимых изменений. Это снижает риск внедрения некорректных патчей, которые могут привести к сбоям в системе или неожиданному поведению. Правильный выбор и применение инструментов проверки гарантируют, что тесты действительно отражают состояние системы, а не просто соответствуют ожиданиям разработчика патча, что в конечном итоге повышает общее качество программного продукта.
